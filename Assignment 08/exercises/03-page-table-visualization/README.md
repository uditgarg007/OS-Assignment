# Question 3: Process Page Table Visualization

## Overview
Visualizing page directories and page tables is essential for understanding the physical layout of an operating system's address space. In xv6, the memory layout is structured as follows:
- **Code and Data**: Mapped to lower virtual addresses (`0x0` to `0x2000`).
- **Stack Guard Page**: Located directly beneath the user stack at `0x2000`. It is generated by `exec()`, which explicitly clears the user-accessible flag (`PTE_U`) using `clearpteu()`.
- **User Stack**: Resides at `0x3000`.
- **Heap**: Dynamic memory allocations grow upwards starting from `0x4000`.
- **Kernel Mappings**: Occupy addresses from `0x80000000` (`KERNBASE`) up to the system's physical memory limits.

This assignment implements the `int vmprint(void)` system call to output this memory hierarchy. The user-space test is `page_table_dump_test.c`.

## Formatting Specification
- **Level 1 (Page Directory Entry)**: `.. pde [idx]: pt_frame=0x..., flags=[P,W,U]`
- **Level 2 (Page Table Entry)**: `.... pte [idx]: va=0x... -> pa=0x..., flags=[P,W,U]`
- **Scope**: Logs all user-space mappings (`va < KERNBASE`) and concludes with a single-line summary of the kernel mapping.

## Stack Guard Page Verification
Within `exec.c`, the system allocates two pages for the user stack and revokes user access on the lower page:

```c
sz = PGROUNDUP(sz);
sz = allocuvm(pgdir, sz, sz + 2*PGSIZE);
clearpteu(pgdir, (char*)(sz - 2*PGSIZE));
In the resulting output dump, this guard page appears as:
.... pte [2]: va=0x2000 -> pa=0xdfdd000, flags=[P,W,-]

Because the PTE_U flag is disabled (represented by -), any user-level instruction attempting to access this address triggers a fatal page fault (trap 14). This hardware-level boundary prevents stack overflows from corrupting the program's code and data segments.
